## 2. Data model (add what migration 0008 created)

- `account_sessions`: id, account_id, session_token_hash, expires_at, revoked_at. Owner account sessions (FR-24), 30 days; only the hash of the cookie secret is stored.
- `auth_attempts`: key, at. Rate-limit counter for sign-up, sign-in and reset; key is a SHA-256 hash of the limit name and the IP or email; rows older than 24 hours are deleted.
- `owner_sessions.account_id`: set when an account owner opens an inbox from /account, so a password reset also ends that inbox session.

## 4. Decisions needed (add under Risks and decisions needed)

- **D-2 App entry point (FR-13).** FR-13 says a signed-in owner who opens the app goes straight to the inbox, and a signed-out owner gets a sign-in screen with an emailed-link option. Since #29, / is the marketing landing page, which has no sign-in link. Decide the owner's entry URL (for example /account, redirecting to the inbox when the business has one location) and whether the landing page links to it.
- **D-3 Password change (FR-24).** FR-24 says "a password change or reset ends all other sessions" but lists no change-password feature. Decide whether v0.1 needs an in-app password change, or only reset.
- **D-4 Breached-password check outage (FR-24).** Main lets the password through when Have I Been Pwned cannot be reached. Decide whether that is acceptable or whether sign-up and reset must refuse (or use a local list) when the check cannot run.
- **D-5 Sign-up switch.** Main shows sign-up only when SIGNUP_OPEN is "true". Decide whether to record this as a requirement (operator-controlled launch of self-serve sign-up).
